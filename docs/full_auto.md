# 회의록 등록부터 업무 배분까지 자동 실행

`full_auto` 브랜치에서는 새 회의록 등록 화면에 **등록 후 업무 배분까지 자동 실행**이 기본으로 선택됩니다. 등록하면 기획서 생성 → 기획서 자동 승인 → 요구사항 생성·자동 승인 → 업무 생성·담당자 추천 → 배분 확정이 순서대로 실행됩니다. 선택을 해제하면 기존 단계별 검토 흐름을 사용합니다. 일반 사원과 PM 모두 자신의 회의록에서 사용할 수 있습니다.

## 팀원 최초 실행

`full_auto` 브랜치를 내려받고 **백엔드와 AI 의존성을 같은 Python 가상환경**에 설치합니다. 프론트엔드는 `frontend`에서 `npm ci`로 설치합니다.

```bash
cd backend
python -m pip install -r requirements.txt
```

`.hwp` 회의록을 읽으려면 Python 패키지 설치와 별도로 `hwp5txt` 명령이 실행 환경에 있어야 합니다. `.docx/.pdf/.txt/.md`에는 필요하지 않습니다.

`backend/.env.example`을 `backend/.env`로 복사하고 `SECRET_KEY`, `OPENAI_API_KEY`, DB 설정을 각자 채웁니다. 로컬 SQLite를 쓰면 `MYSQL_HOST`를 비웁니다. 팀 DB를 쓸 경우 접속 정보와 기존 직원·프로젝트·스킬 데이터가 필요합니다. `MEETING_SUMMARY_MODEL` 기본값은 `gpt-5`입니다.

설정 화면의 사원별 폴더 감시를 쓰려면 `MEETING_WATCH_ALLOWED_ROOT`에 **백엔드가 읽을 수 있는 상위 폴더**를 지정합니다. WSL 예시는 `/mnt/c/Users/<계정>/Desktop`, Windows에서 Python을 직접 실행하면 `C:\Users\<계정>\Desktop`입니다. 설정 화면에서 각 사원이 이 경로 안의 자기 회의록 폴더를 저장하고 감시를 켭니다. 서버가 다른 컴퓨터에 있으면 사원의 PC 폴더를 직접 볼 수 없으므로 공유 경로 또는 로컬 백엔드가 필요합니다.

## 실행

같은 가상환경을 활성화하고 `backend`에서 마이그레이션을 적용합니다.

```bash
python manage.py migrate
python manage.py runserver
```

별도 터미널에서 같은 가상환경·환경변수·DB를 사용하는 자동 실행 워커를 시작합니다.

```bash
python manage.py run_full_auto_worker
```

프론트엔드는 기존대로 `frontend`에서 `npm run dev`로 실행합니다. 자동 생성에는 기존 AI API 키와 직원·스킬·공통 코드 데이터가 필요합니다. 워커가 없으면 작업은 DB에 `PENDING`으로 보관됩니다. 운영에서는 워커를 프로세스 관리 도구로 유지해야 합니다. `--once`는 대기 중인 작업 하나를 처리한 뒤 종료합니다.

## 상태와 재시도

문서 화면에 현재 단계와 오류를 표시합니다. 새로고침하거나 페이지를 닫아도 워커는 계속 처리합니다. 자동 작업이 완료되기 전에는 같은 문서의 수동 생성·수정·승인 API를 409로 차단합니다.

완료된 기획서와 요구사항 ID를 저장하므로 실패 후 **실패한 단계부터 재시도**를 누르면 해당 문서를 재사용합니다. 재시도는 작성자 또는 PM이 할 수 있고, 담당자 추천은 수정된 인력 정보를 반영해 다시 생성합니다. 담당자가 없는 업무나 요구사항 연결이 잘못된 업무는 확정하지 않습니다. 자동 승인은 이력과 기획서 검토 의견에 명시하며 사람의 검토자로 기록하지 않습니다.

최종 배정 저장과 작업 완료 표시는 하나의 DB 트랜잭션으로 처리합니다. 확정된 업무는 기존 정책과 같은 `PENDING_APPROVAL` 상태로 저장되어 담당자의 업무 목록에 나타납니다. 담당자의 수락·진행·완료까지 자동으로 처리하지는 않습니다.

워커가 강제 종료된 경우 실행 중 작업은 `RUNNING`으로 남습니다. **모든 자동 실행 워커가 종료된 것을 확인한 뒤** 해당 작업 ID를 지정해 복구합니다. 실행 중인 워커가 있는 상태에서 복구하면 AI 호출이 중복될 수 있습니다.

```bash
python manage.py run_full_auto_worker --recover-job <작업-UUID>
```

체크포인트가 저장되기 전에 프로세스가 종료되면 그 단계의 AI 호출은 다시 수행될 수 있습니다. 자동 무한 재시도나 운영 DB 변경은 수행하지 않습니다.

## API

- `POST /api/meetings/notes/`: `auto_run: true`로 자동 실행. 생략 시 모든 계정에서 true.
- `GET /api/meetings/notes/{id}/full-auto/`: PM 또는 회의록 작성자가 상태 조회. 수동 문서는 `{"job": null}`.
- `POST /api/meetings/notes/{id}/full-auto/`: 작성자 또는 PM이 실패한 작업을 재시도하거나, 아직 요구사항이 없는 기존 회의록의 자동 작업을 시작. 대기·진행·완료 작업은 409.

## 검증

```bash
python manage.py test meetings.test_full_auto
```

AI 응답을 모의 처리하고 실제 테스트 DB의 자동 승인·업무 저장, 권한, 중복 실행 방지, 실패 중단 및 재시도를 검증합니다. 실제 외부 AI 호출과 운영 MySQL 동시 워커 부하 검증은 별도로 필요합니다.

자동 작업이 없는 기존 회의록은 문서 화면의 **이 회의록으로 자동 업무 배분 시작** 버튼으로 실행할 수 있습니다. 워커 코드를 수정한 뒤에는 워커를 재시작해야 합니다(개발 웹 서버와 달리 자동 재로딩하지 않습니다).

기획서만 이미 생성한 회의록은 그 기획서를 재사용하고 요구사항 생성부터 이어갑니다. 기존 요구사항이 있는 문서는 덮어쓰지 않도록 수동 흐름을 유지합니다.

## 날짜 폴더의 회의록을 통합해 자동 배분

백엔드와 같은 PC에서 실행하는 로컬 명령입니다. 폴더 이름은 `YYYYMMDD`여야 하며 바로 아래의 `.docx/.pdf/.txt/.md/.hwp` 파일을 모두 읽습니다. 파일 하나라도 읽지 못하거나 비어 있으면 전체를 중단합니다. 각 파일 요약과 통합 요약은 LLM이 생성하며, 출처 이름과 SHA-256을 남깁니다. 원본 파일은 수정하지 않습니다.

```bash
cd backend
python manage.py import_daily_meetings "/mnt/c/Users/Playdata/Desktop/회의록/20261006" --project-id 123 --username 계정명
```

기본 출력은 원본 폴더 옆의 `20261006_summary/최종_회의록_요약본.md`와 `.sources.json`입니다. 요약본의 결정·보류·충돌을 검토한 다음 같은 명령에 `--apply`를 붙이면 해당 프로젝트에 요약 회의록 한 건을 등록하고 Full Auto 작업을 예약합니다. 이때 기존 요약본을 다시 생성하지 않으며 원본 파일 해시가 달라졌으면 중단합니다.

```bash
python manage.py import_daily_meetings "/mnt/c/Users/Playdata/Desktop/회의록/20261006" --project-id 123 --username 계정명 --apply
python manage.py run_full_auto_worker
```

워커는 기획서 생성·자동 승인 → 요구사항 생성·자동 승인 → 업무 추천·배분 확정을 이어서 처리합니다. 폴더 수집 명령은 다른 컴퓨터의 Windows 경로에 직접 접근할 수 없으므로 파일이 있는 PC에서 실행해야 합니다. 요약 모델은 `MEETING_SUMMARY_MODEL` 또는 `--model`로 바꿀 수 있고 기본값은 `gpt-5`입니다. 동일 파일 묶음과 프로젝트의 재등록은 건너뜁니다. 원본이 바뀌면 별도 요약본 출력 폴더를 지정해 다시 검토하세요.

### 폴더 자동 감시

날짜 폴더 하나 또는 그 상위 폴더를 지정해 감시 명령을 계속 실행합니다. 현재 PC의 경로만 읽습니다. 기본적으로 5초마다 확인하고, 파일 목록·크기가 30초 동안 바뀌지 않으면 전체 파일을 다시 요약해 바로 등록하고 Full Auto 작업까지 이 프로세스에서 실행합니다. 워커를 따로 실행할 필요는 없습니다.

```bash
cd backend
python manage.py watch_daily_meetings "/mnt/c/Users/Playdata/Desktop/회의록" --project-id 123 --username 계정명
```

같은 파일 묶음은 해시로 식별해 재시작해도 재등록하지 않습니다. 파일이 추가되거나 바뀌면 새 통합 요약본과 새 자동 배분 작업이 생성됩니다. 버전별 산출물은 `20261006_summary/<해시>/`에 저장합니다. 새 버전은 기존 배정 업무를 삭제하거나 교체하지 않으므로, 여러 버전의 배정이 필요 없는 프로젝트에서는 이전 버전의 업무를 확인해야 합니다. 실패한 자동 작업은 `ERROR`로 남으며 자동 재시도하지 않습니다. 감시 명령이 종료되어 있으면 파일 추가를 감지하지 못하므로 운영에서는 작업 스케줄러나 프로세스 관리 도구로 계속 실행하세요.

### 웹 설정 화면에서 사원별 감시 ON/OFF

백엔드 `.env`에 `MEETING_WATCH_ALLOWED_ROOT`를 설정합니다. 이 경로는 각 사원이 지정할 수 있는 감시 폴더의 상위 경로이며 백엔드 프로세스에서 실제로 접근할 수 있어야 합니다. WSL 예시는 `/mnt/c/Users/<계정>/Desktop`이고 Windows에서 Python을 직접 실행하면 `C:\Users\<계정>\Desktop`입니다. 서버를 재시작하면 각 사원이 설정 화면 맨 아래에서 자신의 폴더 경로를 입력해 **감시 폴더 저장**을 누르고, 프로젝트를 선택해 감시를 켤 수 있습니다. WSL에서 입력한 Windows `C:\...` 경로는 `/mnt/c/...`로 변환됩니다. 허용 경로 밖이거나 존재하지 않는 폴더는 거부합니다.

각 사원의 감시는 별도 프로세스로 작동합니다. `YYYYMMDD` 폴더의 파일 상태가 30초간 안정되면 파일별 요약 → 통합 요약 → 회의록 등록 → 기획서·요구사항 생성 → 업무배분을 실행합니다. 다른 사원의 ON/OFF에는 영향이 없습니다. OFF는 새 폴더 처리를 막고 이미 실행 중인 AI 작업이 끝난 뒤 해당 사원의 프로세스를 종료합니다. 새 파일 묶음은 새 업무 배분을 만들며 기존 배정 업무는 자동 정리하지 않습니다. 백엔드가 다른 서버에 배포되어 있다면 그 서버에서 로컬 PC 폴더를 볼 수 있어야 합니다.
