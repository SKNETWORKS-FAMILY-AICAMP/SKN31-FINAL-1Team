# 회의록 기반 기획서 생성 구조 변경 평가서

작성일: 2026-09-21

> 상태: 평가 보류(이전 실험 기록)
>
> 이 문서의 `1~4번·5번·6~7번 병렬 생성` 구조는 후속 품질 검증에서 섹션 간
> 일관성 한계가 확인되어 현재 실행 구조가 아니다. 현재는 `사실·결정 인덱스 →
> 1~7번 전체 단일 생성 → 코드 검증` 구조로 교체되었다. 다양한 유형의 회의록에
> 대한 실제 생성 품질과 시간을 검증한 뒤 비교 수치와 최종 평가를 다시 작성한다.

## 1. 평가 목적

기존의 `회의록 구조화 AI → 기획서 생성 AI` 2노드 구조와, 회의록 원문을
기획서 생성 노드가 직접 읽는 구조를 비교한다. 생성 시간만 줄이는 것이 아니라
기획서 7개 섹션의 완성도, 원문 근거 연결, 확정·미확정 구분 및 다음 단계인
요구사항 정의서 호환성을 함께 검증한다.

## 2. 구조 비교

### 변경 전

```text
회의록 원문
  → 회의록 구조화 AI
  → 구조화 결과의 근거·정합성 검증
  → 기획서 생성 AI
  → 기획서
```

장점은 기능과 인용을 구조화한 중간 데이터가 이미 존재한다는 점이다. 반면 첫
노드에서 누락되거나 잘못 분류된 내용은 기획서 노드가 원문으로 복구하기 어렵고,
동일 내용을 두 AI가 연속으로 해석한다. 무신사 장문 회의록 실측에서는 구조화
단계가 전체 시간의 대부분을 차지해 총 생성 시간이 약 268.5초였다.

### 변경 후

```text
회의록 원문
  → 기획서 생성 노드
      ├─ 1~4번: 개요·목표·세부 목표·사용자
      ├─ 5번: 주요 기능과 기능별 원문 근거
      └─ 6~7번: 기술·제약·최종 결정
     위 세 호출을 병렬 실행
  → 코드 기반 인용 검증·기술 설계 필터·결과 병합
  → 기획서
```

외부 파이프라인의 담당 노드는 하나로 줄지만, 내부 책임은 세 생성 작업으로
분리한다. 각 작업은 회의록 원문 전체를 직접 확인하고 결과를 기존 7개 섹션
계약으로 병합한다.

## 3. 변경 이유

1. 중간 구조화 과정에서 발생하는 정보 손실을 줄인다.
2. 같은 회의록을 구조화와 작문 단계에서 연속으로 재해석하지 않는다.
3. 기획서 목적을 알고 있는 모델이 원문에서 섹션별 사실과 결정 관계를 직접
   판단하게 한다.
4. 기능 내용과 기능별 인용을 같은 생성 결과에서 받아 의미 불일치를 줄인다.
5. 확정 결정은 `[기능]`, `[기술]`, `[데이터]`, `[범위]`,
   `[비기능 요구사항]` 형태로 하류에 보존한다.
6. 긴 선행 AI 구조화 단계를 제거해 사용자가 기다리는 시간을 단축한다.

한 번의 거대한 모델 응답으로 1~7번을 모두 생성하는 방식은 채택하지 않았다.
무신사 회의록 최초 실험에서 1~5번을 한 스키마에 묶었을 때 필드 누락으로 네 번
재시도한 뒤 실패했다. 이를 근거로 1~4번, 5번, 6~7번을 분리하고 병렬화했다.

## 4. 품질 안전장치

- 모든 인용은 코드가 실제 회의록 원문과 대조한다.
- 원문에서 검증되지 않은 인용은 근거 목록에서 제외하고 PM 확인 사항으로 남긴다.
- 회의에서 명시한 `주요 기능 N개` 또는 `1차 기능 목록`을 우선한다.
- 알림, 감사 기록, 다운로드 대체 경로 같은 하위 조건은 관련 기능 설명에 합친다.
- 별도로 확정된 인증·외부 시스템 연동만 `별도 연동`으로 분리한다.
- S3/RDS 분리, 테이블·스키마 설계, 학습 인프라처럼 구현 전용인 항목은 주요
  기능에서 코드로 제거하고 기술 섹션에만 둔다.
- 미확정 기준에 대해 원문에 없는 임시값이나 대체 운영 방식을 만들지 않는다.
- 최종 결정과 PM 확인 사항을 분리하며, 범위 제외·이관 내용은 요구사항 기능으로
  생성하지 않는다.
- 최종 결정을 문서 전체의 기준으로 사용해 이미 확정된 주제의 PM 질문을 제거한다.
- 미확정 질문과 충돌하는 기능 설명의 단정 문장은 제거하고 확정된 기능 동작만 남긴다.
- 대상 사용자는 `확인된 사용자`와 `제안 사용자`로 나누고 제안 사용자 질문은
  하나로 통합한다.

## 5. 실측 결과

| 입력 | 길이 | 결과 | 생성 시간 |
|---|---:|---|---:|
| 무신사 장문 회의록 | 29,372자 | 7개 섹션 모두 생성 | 42.0초 |
| 러닝패스 범위 확정 회의 | 3,395자 | MVP 5개·별도 연동 분리, 결정 10건 보존 | 37.2초 |
| 정보가 모호한 리테일링크 회의 | 944자 | 확정 기능 2개만 생성, 미정 내용 분리 | 23.8초 |

무신사 회의록은 실행별 API 응답 편차로 42.0~66.6초가 측정됐다. 변경 전 전체
실측 약 268.5초와 비교하면 대기 시간이 약 75~84% 감소했다.

최종 무신사 결과에서는 7개 섹션이 모두 생성됐고, 기술 설계 항목을 제거한 주요
기능 10개가 남았다. 모델이 작성한 기능 근거 30개는 원문 검증을 통과했다.

## 6. 요구사항 정의서 연계 검증

무신사 기획서를 DB에 저장하지 않고 요구사항 생성기에 직접 전달했다.

- 전체 요구사항: 21건
- 기능 요구사항: 16건
- 비기능 요구사항: 5건
- `[범위]` 결정의 기능 오생성: 없음
- 기본 보안·성능 요구사항: `검토대기` 유지
- 기술·데이터 결정: 비기능 요구사항에 반영

기획서 HTML에서 기능명과 설명을 항목별로 분리하도록 백엔드를 보완했다. 최종
결정의 화면용 HTML과 별도로 태그가 붙은 구조화 항목을 저장하고, 요구사항
생성기는 구조화 항목을 우선 사용한다.

## 7. 자동 검증 결과

- AI 테스트: 399개 통과, 2개 제외
- 변경 관련 Django 테스트: 9개 통과
- 프론트엔드 Vitest: 35개 통과
- TypeScript: 통과
- Python 문법 및 `git diff --check`: 통과

전체 저장소 검사에서는 이번 변경과 무관한 기존 실패가 확인됐다.

- Django 전체 41개 중 사용자 비밀번호 PATCH 응답 형식 테스트 1개 실패
- 전역 ESLint: 기존 코드와 study-notes를 포함해 178개 오류, 12개 경고

위 실패 파일은 이번 기획서 생성 변경 범위에 포함되지 않아 수정하지 않았다.

## 8. 최종 평가

새 구조가 기존 구조보다 적합하다. 중간 AI 구조화 결과에 의존하던 정보 손실과
긴 대기 시간을 줄였고, 원문 직접 생성·인용 검증·구조화 결정 전달을 통해 다음
요구사항 정의서 단계도 유지했다.

기존 회의록 구조화 코드는 비교 및 회귀 확인을 위해 남겨두되, 웹 서비스의
기획서 생성 실행 경로에서는 호출하지 않는다. 운영 확인 항목은 실제 웹에서
기획서 생성 후 다음 세 가지를 확인하는 것이다.

1. 기능별 `원문 보기`가 해당 기능 인용을 표시하는가.
2. 최종 결정의 확정 내용과 PM 확인 사항이 분리되어 보이는가.
3. 승인된 기획서로 요구사항 정의서를 생성했을 때 범위 제외 항목이 기능으로
   생성되지 않는가.
