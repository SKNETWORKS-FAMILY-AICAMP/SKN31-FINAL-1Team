## 1. 테스트 개요 및 범위

### 1.1 목적

동시 사용 시 일반 API의 응답시간과 오류율, AI 작업의 실제 완료시간과 처리량, 서버·DB 자원 사용량을 측정한다. AI 처리 중 일반 업무의 성능 저하, 동일 문서의 동시 변경으로 인한 중복·유실, 장애 후 복구 가능 여부를 확인한다.

### 1.2 포함·제외 범위

| 구분 | 내용 |
| --- | --- |
| 포함 | 로그인·토큰 갱신, 대시보드, 목록·상세 조회, 업무 수정·승인·확정, AI 생성·상태 폴링, 문서·음성 처리, 혼합 부하, 지속 부하, 경합·복구 |
| 별도 관리 | AI 의미 품질·환각·커버리지 평가는 기존 품질 보고서에서 관리. 본 문서에서는 결과 존재·스키마·DB 정합성·기능 완료 여부를 확인 |
| 제외 | 전면 보안 진단, UI 사용성 평가, 운영 서비스의 무제한 스트레스 테스트 |

### 1.3 현재 구조 및 병목 후보

서비스 테스트 보고서(2026-09-28)에 따르면 배포 경로는 브라우저 → Vercel(Next.js 프록시) → AWS EC2(nginx·Gunicorn·Django) → AWS RDS(MySQL 8.4)이다. 이는 문서상 배포 구성이며 현재 운영 서버에 직접 접속해 재확인한 값은 아니다. AI 생성은 Job 레코드 생성 후 daemon 스레드에서 실행하며, 접수 API는 202와 job_id를 반환한다. 프론트는 약 1.5초 대기 후 상태를 다시 조회한다. 음성 업로드의 직접 백엔드 호출 경로도 별도로 재현한다.

| 관찰한 구현 | 검증할 가설 |
| --- | --- |
| AI 시작 요청마다 Job·스레드 생성 | 동시 실행 증가 시 스레드·DB 연결·외부 호출 증가. 같은 문서 중복 실행 시 결과 충돌 가능성 |
| 진행 상태 폴링 | 대기 화면 증가에 따른 조회 부하. 응답시간을 제외한 이론적 요청량은 화면 수 ÷ 1.5초이며 실제값은 별도 측정 |
| 대시보드 프로젝트별 업무 집계 | 프로젝트 증가에 따른 쿼리 수·응답시간 증가 |
| 재시도·타임아웃 설정 | retry_config의 30초 상수만으로 전체 호출 제한을 보장할 수 없음. 공통 클라이언트 생성부에는 명시적 timeout 인자가 없어 호출별 적용 확인 필요 |
| 대용량 음성 FFmpeg 처리 | 파일 크기·음성 길이에 따른 CPU·메모리·임시 디스크 및 HTTP 처리시간 증가 |
| daemon 스레드 기반 작업 | 프로세스 재시작 시 작업 중단 및 RUNNING 잔류 여부 |

위 내용은 코드에 근거한 검증 가설이며, 부하로 재현된 결함이나 측정 결과가 아니다.

## 2. 테스트 환경 및 실행 준비

### 2.1 최초 사전 점검 결과 — 이력

아래 표는 로컬 MySQL 복제·테스트 준비 이전의 점검 이력이다. 이후 로컬 DB 연결과 합성 데이터·HTTP 서버 구동이 완료됐으며 최신 상태는 7장과 13장을 참조한다.

환경변수는 설정 유무만 확인하였다. 비밀값은 보고서에 기록하지 않으며 DB 연결, AI 실호출, 부하 발생은 수행하지 않았다. 설정 존재는 연결 성공의 증거가 아니다.

### 2.2 실행 환경 구분

| 환경 | 목적 및 조건 |
| --- | --- |
| 로컬 사전 검증 | 격리 DB·합성 데이터·AI 모의 응답으로 시나리오 검증. 같은 장비에서 서버와 부하 발생기를 실행한 수치는 운영 용량으로 해석하지 않음 |
| 배포 환경 검증 | Vercel → EC2 nginx·Gunicorn → RDS 구성을 기준으로 준비. EC2/RDS 사양·워커 수는 미확정. 별도 발생기로 동일 API·인증·데이터의 프록시 및 직접 경로 비교 |
| 실제 AI 검증 | 모델·추론 설정·입력 크기 고정, 호출 예산과 제공자 제한 확인 후 제한된 동시 실행 |

### 2.3 실행 전 필수 확정 사항

① 대상 URL 및 테스트용 DB 분리 ② 상위 가상환경 사용 및 HTTP 구동·마이그레이션 검증 ③ PM·일반 계정 및 합성 데이터 준비 ④ 목표 사용자 수·요청 도착률·합격 기준 합의 ⑤ AI 호출 예산·상한 설정 ⑥ 서버·DB 모니터링 권한 확보 ⑦ 데이터 복구·정리 방법 준비.

로컬 DB 사용은 필수가 아니다. AWS 테스트용 DB를 사용해도 된다. 같은 RDS 인스턴스에서 스키마만 분리하면 CPU·메모리·연결 자원은 공유하므로 한계·복구 테스트는 별도 테스트 인스턴스를 기준으로 한다. 현재 설정은 MYSQL_HOST가 있으면 MySQL을 사용한다. 부하 도구 또는 시드 실행 전에 실제 선택된 DB가 테스트 전용인지 확인한다. 공유 DB에 테스트 데이터를 생성하거나 초기화하지 않는다. 기본 Django 테스트 클라이언트 호출 결과는 네트워크·웹서버 부하 결과와 구분한다.

## 3. 데이터 및 부하 모델

### 3.1 테스트 데이터 계획 — 잠정

| 축 | 소규모 | 기준 규모 | 증가 규모 |
| --- | --- | --- | --- |
| 직원 / 프로젝트 / 업무 | 20 / 10 / 200 | 100 / 50 / 2,000 | 500 / 200 / 20,000 |
| 회의록 입력 | 약 2천 자 | 약 1만 자 | 약 3만 자 |
| 요구사항 / 배정 후보 | 10 / 20 | 30 / 100 | 100 / 500 |
| 음성 파일 | 5MB / 약 5분 | 30MB / 약 30분 | 100~200MB / 약 60~120분 |

위 값은 운영 분포를 확보하기 전 탐색용 데이터다. 음성 길이와 용량은 독립적으로 기록하고 유효한 파일을 사용한다. 문서 파싱은 10MB 이하의 정상 파일과 크기 경계 초과 파일을 구분한다. 생성 데이터는 난수 시드와 생성 스크립트 버전을 기록한다.

정상 부하는 사용자별·시나리오별 문서를 분리한다. 동일 문서·동일 업무 ID 공유는 경합 시나리오에서만 의도적으로 수행한다. PM 권한은 현재 코드의 is_staff 등 실제 권한 조건을 충족하도록 구성한다.

### 3.2 일반 사용자 행동 비율 — 시작안

| 행동 | 비율 | 재현 조건 |
| --- | --- | --- |
| 대시보드 | 25% | PM·일반 사용자 분리 |
| 프로젝트·업무 목록/상세 | 40% | 화면 이동에 필요한 연속 요청 반영 |
| 문서·직원·알림 조회 | 25% | 데이터 크기별 응답량 기록 |
| 업무 상태 변경·문서 수정 | 10% | 유효한 상태 전이 및 CSRF 포함 |

로그인은 사용자 세션 시작 시 수행하고 이후 쿠키를 유지한다. 일반 사용자 80%, PM 20%, 행동 간 대기 2~5초를 시작안으로 사용한다. 로그인 급증과 토큰 만료·갱신은 별도 시나리오로 분리한다. AI 생성·폴링은 위 비율과 독립된 부하로 추가한다.

### 3.3 단계 및 반복

| 단계 | 계획 |
| --- | --- |
| 기준 측정 | 사용자 1명, AI 1건. HTTP 준비 호출 후 일반 API 5분, AI 기능·입력별 최소 5건을 시작안으로 설정 |
| 단계 부하 | 일반 사용자 10 → 30 → 50 → 100명. 단계 전환 1분, 유지 5~10분 |
| AI 동시 실행 | 1 → 2 → 5 → 10건. 단계별 모든 Job 종료 또는 관찰 상한까지 추적 |
| 혼합 부하 | 일반 사용자 목표 부하 + AI 동시 실행 + 실제 UI 간격의 폴링 |
| 급증 | 목표 정상 부하의 2~3배를 1분 유지 후 정상 부하로 5분 회복 관찰 |
| 지속 | 안정적으로 통과한 목표 부하를 1~2시간 유지 |

일반 API 주요 조건은 최소 3회 반복하고 실행 순서·워밍업 조건을 동일하게 유지한다. AI 소표본은 개별 시간·최솟값·중앙값·최댓값·표본 수를 보고하며 p95를 안정적인 용량 근거로 해석하지 않는다. 실제 AI 반복 수는 예산 확정 후 결정한다.

사용자 수와 처리량은 다르다. 느려질 때 요청 발생도 감소하는 사용자 기반 모델 외에, 목표 도착률을 유지하는 별도 시나리오로 포화 여부를 확인한다. 목표 도착률·실제 도착률·부하 발생기에서 시작하지 못한 요청도 기록한다.

## 4. 상세 테스트 시나리오

아래 경로는 /api/ 기준이다. 단일 사용자 사전 측정은 11장, 5·10·20명 단기 탐색은 12장, 20명·5분 최초 실행은 13장, 같은 조건의 총 3회 비교는 14장에 기록한다. 확장 규모 조회 결과는 15장에 기록한다. 쓰기·AI 및 1~2시간 장시간 실행은 미수행이다.

| ID / 우선순위 | 대상·절차 | 주요 검증 |
| --- | --- | --- |
| PERF-01 / 필수 | users/csrf/, login/, me/, token-refresh/. 동시 로그인 및 만료 후 갱신 | 쿠키·CSRF, 성공률, 로그인·갱신 지연 |
| PERF-02 / 필수 | dashboard/overview/, analytics/. PM·일반 사용자별 반복 조회 | p95·오류율·쿼리 수, 프로젝트 증가 영향 |
| PERF-03 / 필수 | projects/, tasks/assignments/, meetings/specs/, requirements/, users/, notifications/ | 목록·상세 지연, 응답 크기, 쿼리 증가. 특히 요구사항 목록의 과거 2.2초 기록 재검증 |
| PERF-04 / 필수 | 업무 상태 변경, 문서 수정·승인, requirements/{spec_id}/confirm-tasks/ | 정상 상태 전이, 중복·유실·부분 저장·잠금 |
| PERF-05 / 필수 | meetings/notes/{id}/analyze/ → notes/analyze-jobs/{job_id}/ | 202 접수와 SUCCESS 완료 분리, 결과 문서·DB 확인 |
| PERF-06 / 필수 | requirements/{spec_id}/extract/ → extraction-jobs/{job_id}/ | 요구사항 추출 완료율, 오류·누락·단계 지연 |
| PERF-07 / 필수 | requirements/{spec_id}/generate-tasks/ → generate-tasks-jobs/{job_id}/ → task-draft/ | 업무·담당자·일정 결과, Job 완료시간, 초안 정합성 |
| PERF-08 / 필수 | 실행 중 Job에 10·30·100개 화면의 폴링 재현 | 폴링 RPS·DB 부하. Job 생성 수와 조회 화면 수 별도 기록 |
| PERF-09 / 필수 | 일반 API + PERF-05~08 동시 실행 | AI 실행 전후 일반 API 지연·오류율 비교 |

## 5. 측정 지표 및 잠정 판정 기준

### 5.1 측정 정의

| 지표 | 정의 |

| 자원 | 서버/발생기 CPU·메모리·스레드·파일 디스크립터, DB 연결·슬로 쿼리·잠금, 디스크·네트워크 |

실행 ID·시나리오 ID·job_id를 연계한다. 서버 시간은 동기화하고 클라이언트 구간 시간은 단조 시계로 측정한다. 상태 변경 시각을 충분히 기록하지 않으면 정확한 대기시간을 산출할 수 없으므로 계측을 추가하거나 미측정으로 표기한다.

### 5.2 합격 기준 — 실행 전 합의 필요

| 대상 | 잠정 기준 |
| --- | --- |
| 일반 조회 | 목표 부하에서 엔드포인트별 p95 ≤ 1초, 예상치 못한 오류율 < 1% |
| 일반 쓰기·AI 접수 | p95 ≤ 2초, 예상치 못한 오류율 < 1%. AI 완료시간은 별도 판정 |
| 혼합 부하 | 일반 조회 p95 ≤ 1초 유지 및 AI 없는 동일 조건 대비 지연 증가율 ≤ 30% |
| 프록시 회귀 | 동일 조건에서 프록시-직접 평균 응답시간 차이 ≤ 0.3초를 기존 서비스 기준으로 계승. 경로별 p95도 별도 기록 |
| 데이터 정합성 | 중복 업무·변경 유실·잘못된 확정 상태·부분 저장 0건 |
| AI·음성 완료 | 기획서 단일 실행은 기존 서비스 목표 120초를 참고 기준으로 계승. 동시 실행 시 허용시간·완료율 및 다른 AI·음성 기능 기준은 별도 확정 |
| 급증·지속 | 급증 종료 후 5분 이내 목표 응답시간 회복. 메모리 부족·프로세스 종료·연결 고갈 0건 |
| 장애 복구 | 방치 Job 식별과 재실행 절차 검증. 허용 복구시간은 운영 요구에 따라 확정 |

정상 오류와 의도적 오류 주입은 별도 집계한다. HTTP 200이라도 Job 상태가 ERROR이거나 결과가 유효하지 않으면 AI 성공으로 집계하지 않는다. CPU 등 자원 수치는 병목 해석에 사용하며 임의의 단일 임계값만으로 합격을 결정하지 않는다.

### 5.3 중단 조건

정상 요청의 예상치 못한 오류율이 1분간 5%를 초과하거나, 메모리 부족·DB 연결 고갈·데이터 오염이 발생하면 신규 부하를 중단한다. 실제 AI 호출은 사전 합의한 비용·호출 상한 도달 시 중단한다. 진행 중 Job은 가능한 범위에서 계속 관찰하고 중단 이유·시각·잔여 작업을 기록한다. Job 관찰 상한은 단일 실행 기준값을 확보한 뒤 실행 전에 확정한다.

## 6. 실행 절차 및 증적 관리

1) 코드 커밋·변경사항, OS·Python·패키지 버전, 모델 설정, DB·웹서버 구성, 데이터 규모 및 테스트 도구 버전을 고정한다.

2) 테스트 전용 DB와 계정으로 마이그레이션·시드·정상 사용자 흐름을 검증한다. 개발 서버의 결과를 배포 웹서버 결과와 혼합하지 않는다.

3) 외부 AI 경계에서 지연·성공·실패를 모의 구현한다. Job 생성·스레드·폴링·DB 저장 경로는 실제 코드를 실행한다. 모의 결과의 데이터 크기와 형태를 실제 결과에 가깝게 맞춘다.

4) 기준 → 단계 부하 → AI 동시 실행 → 혼합 → 급증·지속 → 경합·복구 순서로 실행한다. 실제 AI는 예산·대상 확정 후 별도로 수행한다.

5) 생성 요청 종료 후에도 진행 중 Job을 관찰 상한까지 추적한다. 정상 완료·실패·미완료를 모두 기록한다.

6) 클라이언트 원시 요청 기록, 서버·DB 모니터링, Job 결과, 정합성 검사 결과를 대조하고 결함을 등록한다. 수정 후 동일 조건으로 재측정한다.

7) 테스트용 데이터만 정리하고 환경·결과·판정을 보고서에 반영한다. 공유 데이터와 기존 산출물은 보존한다.

### 6.1 도구 및 저장 구조 계획

실제 로컬 측정에는 httpx 기반 HTTP 클라이언트와 ThreadPoolExecutor 사용자 루프를 사용했다. http_baseline.py는 임시 HTTPS Gunicorn 실행·종료, staged_reads.py는 개별 쿠키와 가중 조회를 담당한다. 서버 자원은 psutil로 기록했다. Locust는 설치·사용하지 않았다. DB 쿼리·잠금 계측과 AI 부하 스크립트는 미구현이다.
